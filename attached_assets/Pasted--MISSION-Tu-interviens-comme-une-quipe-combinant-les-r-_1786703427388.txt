Tu interviens comme une équipe combinant les rôles suivants :

* Senior Product Manager SaaS spécialisé e-commerce / feed management
* Expert Channable / Lengow / DataFeedWatch / Google Merchant Center

* Product Designer Senior

Le projet existant est une application hébergée sur **Replit** visant à devenir une véritable plateforme professionnelle de **gestion de flux produits inspirée fonctionnellement de Channable**.

L'objectif n'est PAS de simplement produire un rapport.

Ta mission est de :

1. comprendre entièrement l'application existante ;
2. inventorier ce qui est réellement implémenté ;
3. tester chaque fonctionnalité ;
4. identifier les fonctionnalités cassées, partielles, simulées ou absentes ;
5. comparer la logique métier à celle attendue d'un véritable feed manager ;
6. auditer entièrement les parcours UX ;
7. auditer l'interface UI dans ses moindres détails ;
8. identifier les problèmes d'architecture ou de modèle de données ;
9. corriger les problèmes détectés ;
10. implémenter les éléments indispensables manquants lorsque cela est raisonnablement nécessaire au fonctionnement du produit ;
11. automatiser les tests ;
12. refaire tous les tests après correction ;
13. laisser l'application dans un état propre, cohérent, stable et exploitable.

# RÈGLE ABSOLUE

Ne considère JAMAIS qu'une fonctionnalité fonctionne simplement parce que :

* du code existe ;
* un composant React existe ;
* une route API existe ;
* un bouton existe ;
* une table SQL existe ;
* une interface est affichée ;
* un message "success" apparaît.

Une fonctionnalité est considérée comme fonctionnelle UNIQUEMENT si tu peux démontrer que :

**UI → API → logique métier → DB → transformation éventuelle → résultat final**

fonctionne réellement.

Teste les fonctionnalités.

Clique réellement sur les boutons.

Crée réellement des données.

Modifie-les.

Supprime-les.

Recharge la page.

Teste les erreurs.

Teste les cas limites.

Teste les dépendances entre fonctionnalités.

Vérifie les données persistées en base.

Travaille de manière totalement autonome.

Ne me demande pas de :

* tester quelque chose ;
* cliquer sur quelque chose ;
* vérifier une page ;

* inspecter une erreur ;
* choisir entre deux implémentations évidentes ;
* intervenir entre deux étapes.

Inspecte d'abord le projet avant de modifier quoi que ce soit.

Lorsque plusieurs solutions techniques sont possibles, choisis celle :

* la plus robuste ;
* la plus maintenable ;
* la plus simple ;

Ne réécris pas inutilement l'application.

Corrige ce qui doit l'être.

# PHASE 7 — RULE ENGINE

C'est probablement la partie la plus critique de tout le produit.

Audite le moteur de règles comme un moteur de transformation de données professionnel.

Une règle doit suivre une logique :

**IF conditions
THEN actions
ELSE optional actions**

---

## Conditions

Tester notamment les opérateurs disponibles.

Selon les types de champs, vérifier la pertinence de :

Text :

* equals ;
* not equals ;
* contains ;
* not contains ;
* starts with ;
* ends with ;
* regex ;
* is empty ;
* is not empty.

Numbers :

* equals ;
* > ;
* > = ;
* < ;
* <= ;
* between.

Boolean :

* true ;
* false.

Lists :

* contains ;
* does not contain.

Conditions multiples :

* AND ;
* OR.
